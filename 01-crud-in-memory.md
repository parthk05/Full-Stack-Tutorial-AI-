# Lesson 01 — In-Memory CRUD API (No Database)

**Goal:** Get a FastAPI app running with full Create / Read / Update / Delete for one resource (e.g. `items` or `books`), using memory only.

**Rules for you:**
- Do each step yourself. Do not skip ahead.
- After each step marked **Check**, verify before continuing.
- Prefer reading the official FastAPI docs when stuck: https://fastapi.tiangolo.com/
- Best practices are listed as *why* questions — answer them in your own notes.

---

## Phase 0 — Environment

### Step 0.1 — Python
1. Confirm Python 3.10+ is installed (`python --version` or `py --version`).
2. If not, install it from python.org and ensure it is on your PATH.

### Step 0.2 — Project folder
1. Work inside this repo root: `FASTAPI-Tutorial`. --> `cd FASTAPI-Tutorial`
2. Create a virtual environment in the project (name it `.venv`). --->  `python -m venv env-name`
3. Activate it (Windows PowerShell vs cmd differ — look up the correct activate command for your shell). --> `env-name\Scripts\Activate.ps1`

**Check:** Your terminal prompt should show the venv is active.

### Step 0.3 — Dependencies
1. Create a `requirements.txt`.
2. Add at least: `fastapi` and a server to run it (`uvicorn` with the standard extras).
3. Install from `requirements.txt`. --> `pip install -r requirements.txt`

**Check:** You can import `fastapi` in a Python REPL inside the venv.

## Phase 1 — Minimal app that runs

### Step 1.1 — App entry file
1. Create a package or module for the app (common choices: `main.py` at root, or `app/main.py`).
2. Instantiate a `FastAPI` application object.
3. Add one GET route at `/` that returns a small JSON message (e.g. health / welcome).

### Step 1.2 — Run the server
1. Start Uvicorn pointing at your app object, with reload enabled for development. --> `uvicorn main:app --reload`
    `main` is the name of your Python file (main.py).
    `app` is the FastAPI application object (e.g., app = FastAPI()).
    `--reload` tells Uvicorn to restart the server automatically whenever you save changes.
    `--port port_number` sets the port
2. Open the browser (or use curl / Invoke-WebRequest) and hit `/`. --> use curl command or browser or postman

**Check:** You get a JSON response and the process does not crash.

### Step 1.3 — Interactive docs (best practice awareness)
1. Open `/docs` (Swagger UI) and `/redoc`.
2. Note how your route appears automatically.
3. In your notes: *Why does FastAPI generate OpenAPI docs without extra config?*
    Ans:- Decorators, type annotations and pydantic models provide enough structured information for FastAPI to produce an OpenAPI documennt to power
    Swagger and ReDoc automatically

## Phase 2 — Design the resource (before coding CRUD)

### Step 2.1 — Pick one resource
Choose a single noun (e.g. `Item`, `Book`, `Task`). Stick with it for this lesson.
    Lets pick `Book`
### Step 2.2 — Decide the shape
On paper or in comments, define fields, for example:
- `id` (generated by the server)
- a few string / number / bool fields that make sense for your resource
    - `title` str
    - `genre` str
    - `published_year` int
    - `price` float
    - `in_stock` bool

### Step 2.3 — Decide the URL design
Draft these endpoints (do not implement yet):

| Method | Path | Purpose |
|--------|------|---------|
| POST   | `/books` | Create one |
| GET    | `/books` | List all |
| GET    | `/books/{book_id}` | Get one by id |
| PUT or PATCH | `/books/{book_id}` | Update one |
| DELETE | `/books/{book_id}` | Delete one |

**Check:** Your paths are consistent (plural resource name is conventional). Write down whether you will use PUT (full replace) or PATCH (partial update) and why.
    - We use PATCH
    - We use PUT when we always want to update entire object its a clear replace this resource operation while PATCH is used when we have to update
    few attributes out of multiple

## Phase 3 — Pydantic models (request / response)

### Step 3.1 — Schema for create
1. Create schemas/ folder and add a Pydantic model for the **request body when creating** (no `id` from the client).
2. Add field types and basic validation (required vs optional, min length, etc.).

### Step 3.2 — Schema for response
1. Create a model that includes `id` for what the API returns.
2. Decide whether create/update responses reuse the same response model.

### Step 3.3 — Schema for update
1. Create a model for update payloads.
2. If using PATCH: make fields optional. If using PUT: keep required fields clear.

**Check:** You can import the models without errors. In notes: *Why separate create / update / response models instead of one model for everything?*
    - Design pattern as each one represents a different use case and has different rules
---

## Phase 4 — In-memory storage

### Step 4.1 — Store data
1. Choose a simple store: a `dict` keyed by `id`, or a `list`. Prefer a structure that makes lookup by `id` easy.
2. Keep it in module-level memory for now (you will replace this with a DB later).
3. Add a way to generate unique integer (or UUID) ids.

**Check:** Mentally walk through create → read → update → delete against your store. Spot any race / restart issues (data is lost on restart — expected for this lesson).

## Phase 5 — Implement CRUD (one endpoint at a time)

Do these **in order**. Test each in `/docs` before writing the next.

### Step 5.1 — CREATE (POST)
1. Accept your create schema as the body.
2. Generate an `id`, save into memory, return the created object with status `201`.
3. Attach a `response_model` so docs and responses stay consistent.

**Check:** POST works; response includes `id`; a second POST gets a different `id`.

### Step 5.2 — LIST (GET collection)
1. Return all items currently in memory.
2. Empty list is valid when nothing exists.

**Check:** After a few POSTs, GET collection shows all of them.

### Step 5.3 — READ one (GET by id)
1. Path parameter for `id`.
2. If missing: raise an HTTP error with status `404` and a clear detail message.
3. If found: return the item.

**Check:** Valid id works; unknown id returns 404 (not 500).

### Step 5.4 — UPDATE (PUT or PATCH)
1. Path `id` + body with your update schema.
2. 404 if id does not exist.
3. Apply changes in memory and return the updated item.

**Check:** Update changes only what you intended; GET by id reflects the change.

### Step 5.5 — DELETE
1. Path `id`.
2. 404 if missing.
3. Remove from memory; return an appropriate status (`204` with no body, or `200` with a message — pick one and stay consistent).

**Check:** After delete, GET by id is 404; list no longer includes it.

## Phase 6 — Polish & best practices (still no DB)

### Step 6.1 — Status codes
Review each route and confirm you use the right status codes (`200`, `201`, `204`, `404`). Fix any mismatches.

### Step 6.2 — Error consistency
1. Use FastAPI/Starlette HTTP exceptions (or equivalent) for not-found cases.
2. Avoid bare `Exception` for client errors.

### Step 6.3 — Typing & response models
1. Ensure every route declares `response_model` where a body is returned.
2. Ensure path/query/body parameters have clear types.

### Step 6.4 — Project structure (light refactor)
If everything is still in one file and it feels crowded:
1. Split into something like: `main.py` (app + include routers), `schemas.py` (Pydantic), `routers/<resource>.py` (routes), maybe `storage.py` (the dict).
2. Wire the router with `APIRouter` and `include_router`.

**Check:** App still runs; all five operations still work via `/docs`.

### Step 6.5 — Manual test script (optional)
1. Write a short list of curl / PowerShell commands covering the happy path and a 404 case.
2. Run through them once end-to-end.
